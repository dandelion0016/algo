# 自律型フェーズゲート開発ワークフロー

エージェントは各フェーズ内の作業を完全自律で完遂し、フェーズの節目でのみユーザーの明示的な承認を待つこと。

---

## 開発フェーズ構成

```text
【Phase 0-A: 要件定義 ＆ 初期基盤構築】
  管理者 ＋ システムアーキテクト (`system-architect`)
  ├─ 1. 要件定義書の自律作成 (specs/requirements.md)
  └─ 2. Walking Skeleton（DB・API・フロント疎通）の一気通貫構築
       │
       ▼ 【人間レビュー ＆ 要件・基盤FIX承認ゲート】

【Phase 0-B: システム設計書作成（専門領域別ドキュメント自律策定）】
  各専門サブエージェント ＋ システムアーキテクト
  ├─ 1. フロントエンド設計（画面遷移、UI仕様・バリデーション、HITL承認UI）
  ├─ 2. バックエンド設計（API仕様、業務シーケンス、バリデーション・エラー規約）
  ├─ 3. データベース設計（ER図、テーブル定義、RLS・マルチテナント分離）
  ├─ 4. セキュリティ設計（多層防御、認証認可、脅威分析、監査ログ）
  ├─ 5. SRE・運用設計（SLO/SLI・可観測性、アラートマトリクス、Runbook初動フロー、DR・バックアップ、CI/CDパイプライン）
  ├─ 6. インフラ基盤設計（クラウド構成図、ネットワーク・通信経路、IaC構成、IAM最小権限）
  └─ 7. システムアーキテクトによる領域間インターフェース・整合性の横断点検
       │
       ▼ 【人間レビュー ＆ 設計書FIX承認ゲート】

【Phase 0-C: 開発環境整備 ＆ MCP・権限設計・疎通確認】
  エージェント・AI担当 (`role:agentic`)
  ├─ 1. 承認済み設計書に基づくMCP設定および各担当サブエージェントの権限周り設計
  ├─ 2. 人間が実施すべき初期作業（AWSアカウント、IAMロール等）の作業依頼書作成
  │    │
  │    ▼ 【人間作業: AWSアカウント・初期IAMロール等の作成】
  │    │
  └─ 3. 人間作業完了後の疎通確認（AWS接続・MCP接続・DB疎通テスト）
       │
       ▼ 【人間による環境整備完了 ＆ Phase 1移行承認ゲート】

【Phase 1: 自律実装 ＆ 継続的受入・仕上げ (Continuous Delivery & Feedback)】
  Antigravity AIチーム ＋ 人間ゲートキーパー
  ├─ 1. docs/design/ と初期基盤コードの自律照合・ギャップ問題提起 (`spec-gap-auditor`)
  ├─ 2. 構造化Issueの自動起票（機能・DB・UI・セキュリティ・運用）
  ├─ 3. トピックブランチ新設 ＆ 専門サブエージェント委任（自律実装・自動テスト・Maker-Checker）
  ├─ 4. UAT自動化アシスト: E2E自動テスト・画面キャプチャ・受入サマリレポート提示
  ├─ 5. 人間の実機確認 ＆ フィードバック（UI改善・動作調整）
  │     ★ 実装中の設計乖離検知時: `docs/adr/` に ADR 起票 ─> 人間承認 ─> 設計書追従更新
  ├─ 6. 自動テスト結果構造化サマリ付きPR作成 ＆ 人間マージ承認（Circuit Breaker保護）
  └─ 7. 全設計書要件充足 ＆ 人間による最終検収・リリース承認 🛑【Gate 1: プロジェクト完了】
```

---

## 各フェーズの詳細と停止条件

### Phase 0-A: 要件定義 ＆ Walking Skeleton構築 【管理者 ＋ システムアーキテクト】
- `specs/requirements.md` の作成と、最小限の疎通骨格（Walking Skeleton）を一気通貫で自律構築する。
- **停止条件**: ユーザーが「要件定義と初期基盤をFIX（承認）」するまでPhase 0-Bに進んではならない。

### Phase 0-B: システム設計書作成 【各専門サブエージェント ＋ システムアーキテクト】
- 要件定義書（`specs/requirements.md`）および疎通骨格に基づき、一般的なシステム開発で必要とされる設計書群を各専門サブエージェントが自律作成する。
- **人間が直感的に理解しやすい可読性の徹底**:
  - 全体像・状態遷移・関係性・シーケンスには Mermaid（`flowchart`, `sequenceDiagram`, `erDiagram`, `stateDiagram-v2` 等）を積極活用。
  - API仕様、テーブル定義、環境変数、アラート基準、脅威分析などは構造化されたMarkdownテーブルで明記。
- **作成対象ドキュメント群 (`docs/design/`)**:
  1. **フロントエンド (`docs/design/frontend/`)**:
     - `screen-flow.md`: 画面一覧・画面遷移図（ステートマシン）
     - `screen-specs.md`: UI仕様・画面詳細設計（ワイヤーフレーム、入力バリデーション、コンポーネント構成）
     - `hitl-flow.md`: HITL（Human-in-the-loop）承認モーダル・操作ガード設計
  2. **バックエンド (`docs/design/backend/`)**:
     - `api-spec.md`: API詳細仕様書（エンドポイント、リクエスト/レスポンス型定義、権限スコープ）
     - `sequence-diagrams.md`: ビジネスロジック・ユースケースシーケンス図（例外時挙動含む）
     - `error-handling.md`: バリデーション ＆ RFC 7807準拠エラーハンドリング規約
  3. **データベース (`docs/design/database/`)**:
     - `er-diagram.md`: ER図（エンティティ関係図、カーディナリティ、正規化方針）
     - `schema-spec.md`: テーブル定義書（物理名・論理名、カラム属性、インデックス選定理由）
     - `rls-multitenant.md`: 行レベルセキュリティ（RLS）＆ マルチテナント分離設計
  4. **セキュリティ (`docs/design/security/`)**:
     - `defense-in-depth.md`: 多層防御アーキテクチャ設計書（LLM層、呼び出し層、ツール層、リソース層）
     - `auth-spec.md`: 認証・認可設計書（Inbound/Outbound Auth、JWT/OIDC、ロール権限マトリクス）
     - `threat-modeling.md`: 脅威分析 ＆ 対策表（STRIDE / OWASP Top 10 for LLM、侵入テスト計画）
     - `audit-logging.md`: 監査ログ ＆ トレーサビリティ設計書（ログスキーマ、マスキング規約）
  5. **SRE・システム運用 (`docs/design/sre/`)**:
     - `observability-sli-slo.md`: SLO/SLI ＆ 可観測性設計書（メトリクス、分散トレース、ログ集約）
     - `alert-matrix.md`: 監視アラートマトリクス（しきい値、重大度P1〜P4、通知チャネル）
     - `incident-runbook.md`: インシデント初動 ＆ Runbook基本設計（エスカレーション、ロールバック）
     - `backup-dr-maintenance.md`: バックアップ・DR ＆ 定常運用設計（PITR、シークレットローテーション、脆弱性スキャン）
     - `cicd-pipeline.md`: CI/CDパイプライン設計書（GitHub Actions、品質ゲート、自動ロールバック）
  6. **インフラ基盤 (`docs/design/infrastructure/`)**:
     - `architecture.md`: クラウドインフラ全体構成図 ＆ 方式設計書（マルチAZ、冗長化、サイジング）
     - `network-spec.md`: ネットワーク ＆ 通信経路設計書（VPC、サブネット、SG、通信マトリクス）
     - `iac-spec.md`: クラウドリソース一覧 ＆ IaC設計書（Terraform/CDK、命名規約、タグ設計）
     - `iam-least-privilege.md`: IAM ＆ 最小権限ポリシー設計書（エージェントロール、ワイルドカード排除）
- システムアーキテクトが全ドキュメントを横断点検し、整合性と非機能要件充足を確認する。
- **停止条件**: 全領域の設計書ドラフトを人間向けサマリとともに提示し、**ユーザーから「設計書FIX ＆ Phase 0-C移行承認」を得るまで環境整備を開始してはならない**。

### Phase 0-C: 開発環境整備 ＆ MCP・権限設計・疎通確認 【エージェント・AI担当】
- 承認された設計書（インフラ・IAM・DB等）に基づき、MCP設定、サブエージェント権限設計、人間向けAWS作業依頼書を作成する。
- 人間の作業完了後、疎通テスト（AWS/MCP/DB）を自律実行する。
- **停止条件**: ユーザーから「環境整備完了 ＆ Phase 1移行承認」を得るまでタスク起票・実装を開始してはならない。

### Phase 1: 自律実装 ＆ 継続的受入・仕上げ (Continuous Delivery & Feedback) 【AIチーム ＋ 人間】
- **目的**: Phase 0-Bで策定されたコア設計書群（`docs/design/`）に従い、Phase 0-AのWalking Skeletonを完全な動くプロダクトへ自律的に仕上げ、人間の継続的受入（実機確認・フィードバック）を取り込みながら完成させる。
- **小規模向けアジリティ方針**:
  - ウォーターフォール型の「実装完了後にまとめてUAT」を廃止し、PRごとに「E2E自動テスト・画面キャプチャ・受入サマリ提示」を行うことで、人間が随時実機を触ってフィードバックできる継続的受入（Continuous Acceptance）サイクルを回す。
- **自律実行サイクル (`@autonomous-gap-resolver`)**:
  1. **ギャップ監査・問題提起**: `spec-gap-auditor` が設計書と現在のコードを照合し、未実装機能・未達非機能要件を自律検出。
  2. **Issue自動起票**: 構造化Issue（背景、対象設計書、DoD、担当チーム）を自動起票。
  3. **トピックブランチ実装**: 最新 `main` から `feature/issue-<num>-<slug>` を作成し、専門サブエージェント（`db-agent`, `backend-agent`, `frontend-agent`, `infra-agent`, `security-auditor`, `sre-ops-agent`）が実装・単体テスト・Maker-Checkerレビューを推進。
  4. **設計乖離時の ADR 起票**:
     - 実装中に設計変更や新たな技術選定が生じた場合、独断でコードを変えずに [`docs/adr/`](file:///docs/adr/) に ADR を起票（PROPOSED）して人間の承認を仰ぐ。承認後、ステータスを ACCEPTED にして設計書群を同期更新する。
  5. **UAT自動化アシスト ＆ PR作成**:
     - Playwright E2E自動テスト、画面キャプチャ、専門チーム別自動テスト結果構造化サマリ（Markdownテーブル）を添えてPRを作成（`Closes #<num>`）。
  6. **人間の実機確認 ＆ フィードバック ＆ マージ**:
     - 人間はPR本文のテストサマリと画面キャプチャを確認し、必要に応じてローカル/ステージングで実機操作。
     - 気になる点やUX改善要望があればフィードバックを提示し、AIチームが即座に反映。
     - 問題がなければPRをマージ承認。
  7. **タスク進捗の自律更新（GitHub Projects）**:
     - Issue完了・PRマージに伴うステータスは [GitHub Projects ボード](https://github.com/users/dandelion0016/projects/1) へ自律的に同期する。
     - **日常的なタスク進捗更新に伴う人間ゲートキーパーへの承認要請は一切不要**（自動同期して即座に次のIssueへ継続）。
     - 未解決ギャップが解消されるまで自律サイクルを継続する。
- **サーキットブレーカー保護**:
  - テスト失敗の連続リトライ（5回以上）や同一ファイルの短時間編集ループ（6回以上）が発生した場合、`circuit-breaker-guard` が作動して自律実行を一時停止し、人間の介入（HITL）を求める。
- **停止条件**: 全設計書項目の実装・テストが完了し、人間による最終実機検収が得られた後、**「本番リリース・プロジェクト完了承認（Gate 1）」** を得て完了する。
