# アーキテクチャ決定記録（ADR）プロトコル

本リポジトリでは、設計書（`docs/design/`）の形骸化（Documentation Drift）を防ぎ、小規模〜中規模開発のアジリティとドキュメント品質を両立させるため、以下の ADR 運用ルールを厳格に遵守すること。

---

## 1. 独断による仕様・アーキテクチャ変更の禁止
- 専門サブエージェント（`backend-agent`, `frontend-agent`, `db-agent`, `infra-agent` 等）は、実装中に以下の事態が発生した場合、**独断で設計書と異なる実装を進めてはならない**：
  1. 設計書に定義されたAPIエンドポイント、パラメータ、レスポンス型の変更
  2. データベースのテーブル構成、リレーション、RLSポリシーの変更
  3. ライブラリ、フレームワーク、主要技術スタックの選定変更
  4. 認証・認可フロー、セキュリティ境界の変更
  5. SREアラート基準や運用Runbookに影響する障害処理の変更

---

## 2. ADR 起票・同期ワークフロー

```text
【1. 課題検知】
  「設計書通りではパフォーマンスが出ない」「ライブラリの制約で別の実装が必要」等を検知
      │
      ▼
【2. ADR 起票 (PROPOSED)】
  システムアーキテクト (`system-architect`) が `docs/adr/XXXX-<title>.md` を作成
  ステータスを PROPOSED とし、コンテキスト、選択肢、推奨方針、影響する設計書を明記
      │
      ▼
【3. 人間ゲートキーパーへの承認要請】
  PR本文またはチャットにて ADR の承認（採択 / 却下）を仰ぐ
      │
      ▼
【4. 承認後の設計書追従同期 (Documentation Sync)】
  承認（ACCEPTED）が得られた後、影響する `docs/design/` 配下のファイルを即座に更新し、
  コード実装と設計書の内容を完全に同期させる
```

---

## 3. ADR テンプレートの遵守
新しく起票する ADR は、必ず [`docs/adr/template.md`](file:///docs/adr/template.md) の構成に従い、以下を漏れなく記述すること：
- 意思決定の背景と解決すべき課題
- 比較検討した選択肢（メリット・デメリット）
- 採択理由
- 影響を受ける `docs/design/` ドキュメント一覧
