# アーキテクチャ決定記録 (Architecture Decision Records: ADR)

本ディレクトリでは、システム開発における重要な技術的・設計上の意思決定（アーキテクチャ、ライブラリ選定、データモデル、セキュリティ方針、運用設計等）の履歴を **ADR（Architecture Decision Records）** として永続化・管理します。

---

## 1. ADR 運用の目的

1. **「なぜその設計にしたのか」の文脈保存**:
   - 将来のチームメンバーや後続セッションのAIエージェントが「過去の意思決定の背景・トレードオフ」を即座に理解できるようにする。
2. **設計書のドリフト（乖離）防止**:
   - 実装フェーズ（Phase 1）において設計書（`docs/design/`）と現実の実装コードで乖離や仕様変更が必要になった場合、AIが独断でコードを変えるのではなく、**「ADR起票 → 人間ゲートキーパー承認 → 設計書追従更新」** のサイクルを機械的に回す。
3. **小規模プロジェクト向けのアジリティ担保**:
   - 初期にすべてを完璧に決め切る（BDUF: Big Design Up Front）のではなく、開発を進める中で発生した技術判断を軽量に記録・更新していく JIT（Just-In-Time）な設計運用を実現する。

---

## 2. ADR の命名規則とステータス

- **ファイル名**: `XXXX-title-in-kebab-case.md` (例: `0001-record-architecture-decisions.md`, `0002-use-fastapi-and-sqlalchemy.md`)
- **ステータス**:
  - `PROPOSED`: 提案中（AI起票後、人間の承認待ち）
  - `ACCEPTED`: 承認・採択（人間ゲートキーパーが承認し、実装に適用）
  - `REJECTED`: 却下（人間が不採用と判断）
  - `DEPRECATED`: 廃止（過去の決定が有効でなくなった）
  - `SUPERSEDED`: 改訂（新しいADRによって上書きされた、リンクを明記）

---

## 3. ADR 起票・承認フロー

```text
【ステップ 1: 乖離・課題の検知】
  実装中、既存の設計書（docs/design/）通りにいかない課題や新たな技術選定が発生
      │
      ▼
【ステップ 2: ADR ドラフト作成】
  システムアーキテクトまたは担当エージェントが docs/adr/XXXX-title.md を PROPOSED で起票
  （課題の背景、採択案、却下案、影響する設計書一覧を明記）
      │
      ▼
【ステップ 3: 人間ゲートキーパーへの承認要請 (HITL)】
  PRまたはチャットにて人間に ADR 承認を要請
      │
      ▼
【ステップ 4: 承認 ＆ 設計書・コード追従】
  人間承認後、ステータスを ACCEPTED に更新
  影響する設計書（docs/design/ 配下）を自動更新して同期
```
