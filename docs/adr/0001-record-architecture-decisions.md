# ADR-0001: アーキテクチャ決定記録（ADR）の採用と設計書追従同期プロトコル

## ステータス
- **状態**: `ACCEPTED`
- **起票日**: 2026-09-28
- **承認日**: 2026-09-28
- **提案者**: 管理者 (`role:manager`) / システムアーキテクト (`role:architect`)
- **承認者**: 人間ゲートキーパー

---

## 1. コンテキストと課題 (Context & Problem Statement)
AIエージェントを活用した自律開発（特にPhase 1のギャップ解消やPhase 2のUATフィードバック）において、初期に策定した設計書（`docs/design/`）と実装コードの間で乖離（Documentation Drift）が発生するリスクがある。
また、小規模〜中規模開発向けスターターキットとして、初期にすべてを完璧に決め切る過剰設計（Big Design Up Front: BDUF）を避けつつも、設計の変更や技術選定の経緯がブラックボックス化するのを防ぐ必要がある。

---

## 2. 検討した選択肢 (Considered Options)
1. **選択肢 1: ADR（Architecture Decision Records）と設計書同期プロトコルの採用**（採択）
   - 実装時の設計乖離を軽量なADRとして起票し、人間承認を経て設計書を追従更新する。
2. **選択肢 2: コードのみを直接修正し、設計書は更新しない**（不採用）
   - 速度は出るが、設計書が陳腐化し、後続エージェントや将来の開発者が混乱するため不可。
3. **選択肢 3: 変更があるたびに設計書群全体の再レビュー・再承認を要求する**（不採用）
   - 人間の承認負荷が高すぎ、小規模プロジェクトの俊敏性が失われる。

---

## 3. 決定事項 (Decision Outcome)
- **採択された方針**:
  - `docs/adr/` 配下に意思決定を Markdown で記録する。
  - 実装中に設計書と乖離する変更が発生した場合、エージェントは独断でコミットせず、ADRを `PROPOSED` で起票して人間に確認・承認を求める。
  - 承認後、ステータスを `ACCEPTED` に更新し、影響を受ける `docs/design/` 配下の設計書を同期更新する。
  - これにより、小規模向けのアジリティを保ちながら、設計書とコードの一貫性を恒久維持する。

---

## 4. 結果・影響とトレードオフ (Consequences)
- **ポジティブな影響**:
  - 設計書の形骸化・ドリフトを防止できる。
  - 「なぜその技術を選んだか」「なぜ設計を変更したか」の意思決定履歴が可視化される。
- **トレードオフ**:
  - ADRの作成と承認の手順が1ステップ加わるが、テンプレートとAIの自律起票によりオーバーヘッドを最小化する。
