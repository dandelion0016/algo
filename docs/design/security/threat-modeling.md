# セキュリティ 脅威分析 ＆ 対策マトリクス (Threat Modeling)

本設計書は、「アルゴ（algo）Web対戦システム」におけるセキュリティ脅威分析を、マイクロソフト提唱の **STRIDE モデル** に基づいて実施し、その対策メカニズムを定義します。
特にオンライン対戦・ボードゲーム特有の「手札覗き見」「スコア改ざん」「BOTによる荒らし」「DDoS・課金破産攻撃」に対する具体的な防御策を定めます。

---

## 1. STRIDE 脅威分析マトリクス (Algo Web Battle)

| 脅威分類 (STRIDE) | 脅威ID | 具体的な脅威シナリオ | 影響度 | 対策・実装メカニズム |
| :--- | :--- | :--- | :---: | :--- |
| **Spoofing**<br>(なりすまし) | `TH-001` | 他プレイヤーのIDやセッションを偽装し、他人の手番で勝手にアタック・降伏する | 高 | ・Cognito JWTによる厳格な署名検証。<br>・各ルーム内の操作リクエストに紐付く `playerId` と認証トークン `sub` の一致検証。<br>・推測不可能な暗号学的ルームID（NanoID 12桁）。 |
| **Tampering**<br>(改ざん) | `TH-002` | ブラウザの開発者ツールやAPI経由で、本来の手札とは異なる数字を主張したり、存在しないカードでアタックする | 極大 | ・**ゲームロジック検証エンジン**: Zodスキーマによる入力制約（0〜11、black/white）。<br>・**サーバー側権威性（Authoritative Server）**: クライアント申告を信用せず、サーバー側保持のカード配列と照合して判定。 |
| **Tampering**<br>(スコア改ざん) | `TH-003` | 勝敗結果をクライアントから直接APIに送信し、戦績・レーティングを不正に釣り上げる | 極大 | ・勝敗判定はサーバー側（Lambda）でゲーム終了イベント時に自動集計・直接DynamoDBへ書き込み。<br>・クライアントからの勝敗申告APIエンドポイントを一切設けない。 |
| **Repudiation**<br>(否認) | `TH-004` | 負けそうになったプレイヤーが通信を切断し、「不正に切断された」「アタックしていない」と主張する | 中 | ・対戦ログ（Turn History）の全件記録。<br>・ターン制限時間（タイマー）超過時の自動失格・ペナルティ処理。<br>・切断時の再接続猶予タイマー（30秒）経過後の自動不戦敗確定。 |
| **Information Disclosure**<br>(情報漏洩) | `TH-005` | ブラウザのDOMインスペクタ、Networkタブ、WebSocketペイロードを覗き見して、伏せられた相手のカード数字をカンニングする | 極大 | ・**Information Hiding 原則**: 相手の伏せカード情報は、クライアント配信前に `{ color, isOpen: false, number: null }` として完全に伏字化。<br>・DOM要素への数字埋め込みを一切排除。 |
| **Denial of Service**<br>(サービス妨害) | `TH-006` | ボットによる短時間の大量リクエストやルーム乱造により、サーバー負荷およびAWS無料枠を枯渇させる（課金攻撃） | 高 | ・CloudFront 自動リクエストレート制限。<br>・API Gateway スロットリング（1 IPあたり毎秒10リクエスト）。<br>・DynamoDBルームのTTL（24時間で自動消滅）。<br>・AWS Budgets $0.01 課金検知アラート。 |
| **Elevation of Privilege**<br>(特権昇格) | `TH-007` | ゲストプレイヤーや一般プレイヤーが、ルームホスト権限（キック、設定変更）や管理者APIを不正行使する | 高 | ・JWTのクレームおよびルーム内ロールによる認可チェック。<br>・管理者エンドポイントのパス分離とIP制限/WAF適用。 |

## 2. 対戦チート対策ディープダイブ

### 2.1 カード覗き見チートの根絶
- **脅威**: アルゴは「伏せられた数字を推理する」ゲームであるため、相手の手札の数字がクライアントに1ミリでも伝達されていれば、拡張機能やスクリプトで100%カンニング可能になってしまう。
- **恒久対策**:
  - Phase 1（CPU対戦）: CPU側の手札数字は、CPU推理ロジック専用のローカルスコープ（あるいは隔離されたWeb Worker / 内部ステート）に閉じ込め、Reactのレンダリングツリーには `number: null` のサニタイズされたオブジェクトのみを渡す。
  - Phase 2（オンライン対戦）: LambdaがWebSocketメッセージを配信する際、受信プレイヤー本人のカード以外はすべて `number: null` に変換して送出。通信パケット自体に相手の数字が存在しないため、パケットキャプチャやDevToolsをどう操作しても覗き見は物理的に不可能。

### 2.2 レーティング談合・切断逃げ対策
- **切断逃げ対策**:
  - 対戦中にブラウザを閉じた場合、相手側には「相手の再接続を待機中（30秒カウントダウン）」が表示される。
  - 30秒以内に復帰しなかった場合、切断側の「投了（不戦敗）」として処理され、相手に勝利ポイントが付与される。
- **談合（故意の八百長）対策**:
  - 同一IPアドレス同士、または短時間に連続マッチングした特定ペア間での対戦結果は、レーティング変動幅を自動減衰させるアルゴリズムを導入。

## 3. 疑似侵入テスト（チート耐性自動テスト）

CI/CDおよびテストスイートにおいて、以下のチートシナリオをVitestで自動検証します：

1. **不正な数字アタックテスト**: `number: 12`, `number: -1`, `number: 3.5`, `number: "seven"` のリクエストを送信し、ゲームエンジンが例外をスローして手番が無効化されることを検証。
2. **手番外操作テスト**: 相手の手番中にアタックイベントを発火させ、状態が遷移しないことを検証。
3. **サニタイズ検証テスト**: 生成された全公開GameStateオブジェクトに対し、`isOpen === false` な相手カードの `number` が例外なく `null` であることをアサーション検証。
